# 아키텍처와 설계 결정

```text
Mihon 공식 호스트
  → BookOrbitSourceFactory (네트워크 없이 3개 Source)
    → BookOrbitSource : HttpSource, ConfigurableSource
      → LibraryFilter (로컬 캐시, 라이브러리 ID + binding 스냅샷)
      → SettingsStore (Keystore AES-GCM + host noBackupFilesDir)
      → BookOrbitRepository (작품·파일 정책, 유계 캐시)
        → FilteredPager (서버 형식 필터 + 방어적 look-ahead)
        → BookOrbitApi (실제 DTO·페이지 계약)
          → BookOrbitHttp (API·표지·페이지 공통 인증, 범위 제한)
            → 공식 BookOrbit 서버
```

## 동적 레지스트리를 먼저 검토한 결과

공식 Mihon v0.21.3 및 main의 `ExtensionLoader.loadExtension`을 조사했다. `SourceFactory.createSources()`는 확장 클래스의 인스턴스를 만들 때 호출된다. 이미 로딩한 APK가 같은 versionCode/설치 종류라면 `alreadyLoaded.copy(store=store)`를 반환하는 분기가 **팩토리 호출보다 먼저** 실행된다. ExtensionManager도 현재 로딩한 확장 맵을 재사용한다. 서버 설정·캐시 변경을 알리는 소스 재등록 API는 Source/ConfigurableSource/SourceFactory에 없다.

따라서 디스크 캐시를 읽는 동적 팩토리는 프로세스 시작 시에는 가능하지만, 최초 연결 후 안내 소스를 실제 라이브러리 소스로 바꾸거나 권한·추가·삭제를 즉시 반영하는 UX를 보장할 수 없다. 일반 목록 새로고침도 팩토리 재실행이 아니다. APK 재설치/프로세스 완전 종료가 필요한 구조를 기본 연결 흐름으로 채택하지 않았다.

**현재 결정: 고정 3슬롯 + 라이브러리 필터.** 각 슬롯을 서버·계정 연결로 사용하고, 기본 라이브러리는 인기에 표시한다. 적용한 연결의 모든 라이브러리는 `Filter.Select<String>`으로 선택한다. `getFilterList()`와 팩토리에는 네트워크 호출이 없다. `supportsLatest=false`와 비어 있지 않은 필터 목록으로 Mihon의 인기 / 필터 버튼을 사용한다. 기본 라이브러리를 바꿔도 같은 서버·계정의 다른 라이브러리 작품은 읽을 수 있다. 각 라이브러리별 저장소와 페이지 커서를 분리하고 소스당 최근 4개 저장소만 유지한다. 밀려난 저장소의 중간 페이지는 기존 페이지네이션 정책에 따라 처음부터 다시 불러와야 할 수 있다.

기존 1.6.1은 고정 6슬롯이었다. 당시 공식 로더 분석에 더해 별도 임시 APK로 수행한 캐시 실험에서는 안내 소스 1개 상태에서 캐시를 라이브러리 3개로 갱신해도 탭 왕복만으로는 갱신되지 않고 프로세스 재시작 후에야 3개가 나타났다. 이는 과거 검증이며 이번 변경에서는 에뮬레이터를 호출하지 않는다. 실험 코드와 재현 기록은 experiments/README.md에 보존한다.

설정의 연결 확인은 초안만 갱신하고, **기본 라이브러리 선택 / 적용**에서 라이브러리 레지스트리와 자격 증명을 함께 적용한다. 새 필터 목록은 소스 화면에 재진입하여 받는다. Mihon 자체 화면을 수정하거나 새 탭을 삽입하지 않는다.

## 소스·작품·챕터의 불변 식별자

- 슬롯 소스 ID: 기존 값을 보존한 `641300700000 + slot` (1~3). 슬롯 4~6은 더 이상 생성하지 않으며 기존 작품의 자동 이관은 지원하지 않는다. 해당 슬롯의 암호화 파일을 임의로 삭제하거나 다른 슬롯에 붙이지 않는다.
- 표시명: `BookOrbit · 슬롯 N`. 라이브러리명과 순서는 소스 ID에 영향을 주지 않는다. APK 업데이트 후 호스트가 이전 소스 목록을 유지한다면 Mihon을 완전히 종료하고 다시 실행한다.
- 연결 범위: 정규화한 HTTPS 기본 URL + `auth/me.id` + libraryId에 대응하는 무작위 128-bit binding ID. 이름·키 회전은 바인딩을 바꾸지 않는다. 다른 서버/계정/라이브러리로 변경할 때는 새 바인딩을 부여한다.
- 작품: `/bo/v1/{binding}/{libraryId}/series/{seriesId}` 또는 `/book/{bookId}`.
- 챕터: 위 작품 경로 뒤 `/book/{bookId}/file/{fileId}`. 제목·권 번호·목록 순서가 변해도 파일 ID는 유지한다.
- 적용한 서버·계정의 라이브러리별 연결을 `libraryBindings`에 보관하며 API 키는 중복 저장하지 않는다. 필터는 표시 순서 대신 선택 당시의 라이브러리 ID와 binding을 사용한다. 상세·챕터·페이지·웹 URL은 저장된 작품 URL로 연결을 찾고, 이미지 클라이언트도 binding으로 해당 라이브러리의 현재 키를 찾은 뒤 origin/기본 경로를 검사한다. 필터나 기본 라이브러리를 바꿔도 이전 작품은 정상 범위에 남는다.
- 서버·계정이 바뀌거나 적용한 목록에서 라이브러리가 사라지면 이전 URL 조회를 거부한다. 최근 과거 연결 12개는 자격 증명 없는 식별자로 보관하여 재적용 시 복원한다. 현재 라이브러리 레지스트리는 이 12개 제한의 영향을 받지 않는다. 더 오래된 연결 복원이나 초기화 후의 자동 이관은 지원하지 않는다.
- 이전 설정에는 `libraryBindings`가 없어도 역직렬화 기본값으로 읽는다. 기존 기본 라이브러리의 binding은 유지하고, 사용자가 연결 확인 후 적용하면 다른 라이브러리 바인딩을 추가한다.
- URL은 동일하지만 서버 DB 자체를 완전히 교체하여 계정/도서 ID를 재사용하는 상황은 서버 인스턴스 UUID API가 없어 자동 검출할 수 없다. 그 경우 빈 슬롯을 쓰거나 기존 슬롯의 연결을 초기화해야 한다. 임의 해시만으로 서버 교체를 검출한다고 주장하지 않는다.

## EPUB 제외와 목록 페이지네이션

서버의 `POST libraries/{id}/books`에 만화 형식 및 `present` 필터를 보내고 그 결과를 시리즈 단위로 묶는다. 형식 필터가 시리즈 묶음 및 페이지네이션 **앞에** 적용되므로, EPUB 전용 시리즈가 먼저 많이 있어도 만화가 뒤 페이지로 밀려 누락되지 않는다. 제목 검색도 같은 경로·같은 필터를 사용한다. 시리즈가 없는 도서는 단독 작품으로 포함한다. 주 시리즈 기준으로 그룹화하며 보조 시리즈에 같은 도서를 중복 등록하지 않는다.

클라이언트도 형식·파일 역할·상태를 검사한다. 서버의 형식 필터는 첨부 파일에도 매칭되므로, 시리즈 대표 카드에 읽을 만화가 없으면 시리즈 도서를 유계 조회하여 뒤의 실제 만화 권을 대표로 고른다. 시리즈 전체가 첨부 파일만 가진 경우 제외하며, 인증/프로토콜 오류는 숨기지 않는다. 첨부 만화만 있거나 잘못된 응답 카드가 걸러진 경우 `FilteredPager`가 다음 유효 서버 페이지를 찾는다. 다음 유효 페이지 하나를 미리 확보하여 실제 유효 결과가 있을 때만 hasNextPage=true를 반환한다. 탐색당 최대 128 서버 페이지를 확인하며 한도 초과·모순된 total/빈 페이지는 명시적 오류다. 실패한 보충 읽기는 커서를 커밋하지 않아 재시도 시 건너뛰지 않는다.

쿼리별 Mutex와 최대 4개 세션, 세션당 최근 32개 결과, 5분 TTL을 적용한다. 이미 만료되거나 밀려난 중간 페이지부터 요청하면 첫 페이지부터 다시 탐색하도록 안내한다. 정상 응답은 서버당 40카드이며 일반적인 1,000개 목록은 총 25페이지 요청이다. 방어적 중복 제거는 유지된 페이지 범위에서 수행한다. 서버의 offset 조회에는 snapshot 토큰이 없으므로 조회 중 서버 도서를 삽입/삭제/정렬 변경하면 새로고침이 필요할 수 있다.

## 상세·챕터·페이지

시리즈 도서를 100권씩 libraryId로 제한하여 읽는다. EPUB/PDF/알 수 없는 형식, missing 도서, 첨부 파일을 제외한다. CBZ/CBR/CB7 각각의 content/primary 파일을 챕터로 제공한다. 동일 도서의 여러 만화 판본은 형식이 표시된 별도 챕터다. 권 순서는 서버의 seriesIndex 오름차순을 따르고 Mihon에는 최신 권부터 반환한다. 수치로 해석할 수 없는 권 번호는 -1(미지정)로 두며 파일 ID는 영향을 받지 않는다.

작품 캐시는 2분/최대 16작품/총 10,000파일로 제한한다. 단일 시리즈는 최대 10,000권·10,000 만화 파일, 한 파일은 최대 20,000페이지를 허용한다. 표지 외의 외부 이미지 URL은 받지 않는다. 페이지 요청 전 작품-도서-파일 관계를 다시 확인하고 페이지 수는 실제 파일 API로 확인한다. 디스크에서 삭제되었거나 손상된 아카이브는 상세 목록에서 미리 전부 열어 보지 않으며, 페이지를 열 때 서버의 오류를 명시적으로 표시한다.

## 보안과 호스트 제약

- Android Keystore AES-256-GCM, 슬롯별 AAD, 원자적 쓰기. 저장 위치는 **Mihon 호스트**의 noBackupFilesDir이다. 확장 APK의 allowBackup 설정만으로 호스트 파일이 보호된다고 가정하지 않는다.
- 서버/키 초안과 활성 연결을 분리하여, 입력 도중의 URL과 기존 키를 조합해 네트워크로 보내지 않는다. 인증 성공 후 사용자가 라이브러리 적용을 선택해야 전환된다.
- API 키는 백업 가능한 SharedPreferences나 PreferenceDataStore에 쓰지 않는다. 키 입력창은 비밀번호 형식·자동 저장/자동완성 차단·FLAG_SECURE를 사용한다.
- 공통 비동기 dispatcher의 최대 동시 요청은 4개다. TLS 검증을 해제하지 않으며 HTTPS만 허용한다. 재시도·오류 정책은 API_DISCOVERY.md 참고.
- 요청/응답/서버 주소/자격 증명을 로깅하지 않고 원래 예외의 cause·본문도 전달하지 않는다. 목록 작업 전체는 90초, 상세/페이지 목록 작업 전체는 120초로 제한하여 다중 API 호출도 무한 대기하지 않는다. 다만 호스트 Mihon, 사용자 지정 프록시, 서버 자체 로그 및 Mihon이 별도 저장하는 표지/페이지 캐시는 이 확장이 통제하는 영역이 아니다.
- SourceFactory에는 Context 인자가 없다. 공식 Injekt의 Application 바인딩으로 설정 저장소를 지연 초기화한다. 모든 호스트 API와 Kotlin/OkHttp/serialization/AndroidX 의존성은 compileOnly이며 APK 안에 호스트 스텁을 패키징하지 않는다.

## 미설정 상태의 호스트 호출

Mihon은 소스 화면을 그릴 때 네트워크 요청보다 먼저 HttpSource.getHomeUrl/baseUrl을 읽는다. 따라서 미설정·설정 손상 상태에서도 baseUrl은 예외를 던지지 않고 예약된 .invalid 주소를 반환한다. 실제 목록/API는 설정 오류를 안내하고 설정 화면에 진입할 수 있다. Android 에뮬레이터에서 발견한 초기 화면 크래시를 이 정책으로 수정했다.
